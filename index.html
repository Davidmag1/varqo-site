The integrity gap

Authorized does not mean correct. Success does not mean done.

An AI agent can have the right identity, the right permissions, and a successful tool response — while still acting on a false assumption or leaving the real system in the wrong state.

01 / ACCESS

Identity and authorization

Who is the agent, which systems can it access, and which actions is it permitted to perform?

02 / ACTIVITY

Behavior and tool use

Is the agent risky, overprivileged, off-task, or calling a tool in a dangerous way?

03 / VARQO

Execution integrity

Is what the workflow depends on actually true — and is it safe for the next action to continue?

Evidence, not a concept slide

The core pattern has been exercised against real providers and a real tool-using agent.

The current POC automatically prepares verification, binds runtime identities, independently observes provider-native state, and keeps a dependent action held until required proof passes.

DigitalOceanLive validated

Action completion + resource state

A dependent action remained held until both the asynchronous operation completed and a separate resource read proved the machine was active.

Microsoft AzureLive validated

Runtime-discovered verifier

Varqo safely bound and executed a verifier URL that became available only after the real write response.

AWS CodeBuildLive validated

POST / batch verification

A runtime build identity was bound into an independent batch read and polled from in-progress to its provider-native terminal state.

Tool-using AI agentLive validated

Controlled dependent execution

A real agent attempted to complete its workflow before proof was ready. Varqo held that continuation and released it only after verification.
